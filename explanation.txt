1. PROJECT OVERVIEW & EXECUTIVE SUMMARY
================================================================================
In India, over 140 million farmers produce hundreds of millions of tonnes of 
agricultural commodities (Paddy, Wheat, Maize, Cotton, Pulses) every harvest season.
Government procurement through Agricultural Produce Market Committees (APMCs / Mandis)
and Primary Agricultural Credit Societies (PACS) ensures farmers receive the 
Minimum Support Price (MSP) guaranteed by the Government of India.

However, the physical procurement process suffers from major structural bottlenecks:
1. Long, uncoordinated queues where farmers wait with loaded tractors for 12 to 48 hours.
2. Complete absence of dynamic load-balancing (Centre A has a 200-tractor backlog while
   Centre B, 12 km away, sits underutilized with zero queue).
3. The Digital Divide: Over 60% of rural Indian farmers use basic feature phones without
   internet or touchscreen capability, locking them out of smartphone-only apps.
4. Language barriers: Lack of native voice support in regional Indian languages.
5. Lack of transparency in crop moisture assaying, weighing, and bank credit (DBT).

KISANFLOW SOLVES THIS END-TO-END:
- It provides a single, unified procurement coordination ecosystem.
- Accessible across 4 channels: Web App (PWA), Feature-Phone IVR (`1800-425-4747`),
  Multilingual Voice AI, and Village Assisted Service Desks.
- Fully operational in 6 Indian languages: Telugu, Hindi, Kannada, Tamil, Bengali, English.
- Implements a realistic 5-stage procurement pipeline matching APMC operations.
- Backed by an enterprise relational PostgreSQL database (Supabase) with automated
  sequential daily token numbering per centre.

2. HOW THE PROJECT RUNS (RUNTIME LIFECYCLE & EXECUTION FLOW)
================================================================================
Here is the step-by-step process of how code execution occurs from the moment a user 
runs `npm run dev` to when the browser renders the interactive application:

Step 1: Vite Development Server Initialization
- Command: `vite --port=3000 --host=0.0.0.0`
- Vite reads `vite.config.ts`, loads `@vitejs/plugin-react` and `@tailwindcss/vite`.
- An HTTP development server starts on port 3000 listening on all network interfaces.
- Hot Module Replacement (HMR) is established over WebSockets.

Step 2: HTML Shell & Font Loading (index.html)
- When a user visits `http://localhost:3000`, the browser requests `index.html`.
- `index.html` sets viewport meta tags for responsive mobile/PWA rendering.
- It loads modern Google typography (`Inter` and `Outfit` fonts).
- It injects `<div id="root"></div>` and scripts `<script type="module" src="/src/main.tsx"></script>`.

Step 3: React 19 Hydration & Mount (src/main.tsx)
- Browser executes `src/main.tsx`.
- It imports `createRoot` from `react-dom/client` and loads global styles from `src/index.css`.
- It mounts `<App />` inside `#root` using React 19's concurrent rendering engine.

Step 4: Global Context Provider Wrap (src/App.tsx)
- `App.tsx` wraps the entire component tree with `<KisanFlowProvider>`.
- This initializes the single source of truth (`KisanFlowContext`), which:
  a. Loads active language (defaults to Telugu `'te'` or Hindi `'hi'`).
  b. Checks Supabase cloud database connectivity using `testSupabaseConnection()`.
  c. Fetches live procurement centres, crop MSP rates, and existing registrations.
  d. Initializes local storage fallbacks to guarantee 100% uptime even if offline.

Step 5: Active Portal Rendering (Routing Logic)
- `App.tsx` checks `activeView`:
  - `'landing'`: Renders the high-impact Landing Page with 4-channel access cards.
  - `'login'`: Renders the clean 3-role portal (Farmer / Mandi Operator / Government Officer).
  - `'farmer'`: Renders the comprehensive Farmer Dashboard (slot booking, token, queue, DBT).
  - `'operator'`: Renders the 5-stage Mandi Yard Management Console.
  - `'government'`: Renders the District Analytics & Load Balancing Dashboard.

Step 6: Global Modal & Overlay Management
- Rendered on top of active portals:
  - `Navbar.tsx`: Top bar with 6-language switcher, role indicator, and quick actions.
  - `PhoneSimulatorModal.tsx`: IVR feature-phone telephone simulator with dual-tone audio.
  - `VoiceAssistantModal.tsx`: Multilingual AI voice conversation interface.
  - `SMSDrawerModal.tsx`: Simulated mobile SMS notification slide-out drawer.
  - `DemoTourBar.tsx`: 20-step guided tour toolbar pinned at the bottom for jury evaluation.

4.2 DATABASE & SQL LAYER (supabase/schema.sql)
--------------------------------------------------------------------------------
Contains 315 lines of production-grade PostgreSQL 15 definitions:

- Enums & Custom Types:
  - `user_role_type`: `'farmer'`, `'operator'`, `'government'`, `'support'`.
  - `procurement_stage_type`: `'GATE_ENTRY'`, `'QUALITY_CHECK'`, `'WEIGHING'`,
    `'BAGGING'`, `'J_FORM'`, `'COMPLETED'`, `'REJECTED'`.
  - `procurement_status_type`: Detailed operational states from `WAITING_FOR_GATE_ENTRY`
    to `PROCUREMENT_COMPLETED`.
  - `payment_status_type`: `'PENDING'`, `'INITIATED'`, `'PROCESSING'`, `'CREDITED'`, `'FAILED'`.

- Tables:
  1. `public.profiles`: Stores registered farmers, operators, and government officers
     (phone, masked Aadhaar, village, district, preferred language).
  2. `public.procurement_centres`: Stores PPC centres (Lakshmipur, Ramapuram, Kothuru)
     with daily capacity, active counters, open hours, and status.
  3. `public.crops`: Master data for Paddy, Wheat, Maize, Cotton, Pulses with official MSP.
  4. `public.registrations`: Main transactional table recording farmer slot bookings,
     assigned token number, date, crop, vehicle, and stage progress.
  5. `public.quality_checks`: Moisture %, foreign matter %, assayer name, FAQ compliance.
  6. `public.weighing_records`: Gross weight, tare weight, net weight, weighbridge slip.
  7. `public.bagging_records`: 50kg jute gunny bag count, labour delay flags.
  8. `public.j_forms`: Government digital procurement receipt, total payout, issuing officer.
  9. `public.payments`: DBT transaction details, bank account, payment date, status.
  10. `public.notifications`: SMS and in-app alerts dispatched to farmers.
  11. `public.audit_logs`: Immutable security log of every stage transition and operator remark.

- Stored Procedure `get_next_procurement_token(centre_id, date)`:
  Computes `COALESCE(MAX(token_number), 0) + 1` for that centre and date. Ensures tokens
  always start cleanly at 1 each morning and increment strictly without duplicate collisions.

- Row Level Security (RLS) Policies:
  Enables RLS on all 11 tables with granular read/write policies for public and authenticated roles.

4.6 AUDIO & SPEECH ENGINE (src/utils/audio.ts)
--------------------------------------------------------------------------------
Encapsulates all browser sound generation and speech processing into a clean `SoundController` class:

- `playDTMF(key, durationMs)`:
  - Uses `AudioContext` to synthesize two simultaneous sine-wave oscillators corresponding
    to official telephone keypad frequencies (697Hz to 1477Hz).
  - Implements gain ramps to eliminate audio popping or clicking sounds.
- `playTurnChime()`:
  - Plays a 4-note ascending chord (C5, E5, G5, C6) as audio feedback when a token is called.
- `speak(text, langCode, onEnd)`:
  - Normalizes language to BCP-47 (`te-IN`, `hi-IN`, `kn-IN`, `ta-IN`, `bn-IN`, `en-IN`).
  - Prioritizes regional Indic voices installed in the operating system.
  - Implements `waitForVoices()`: Polls every 150ms for up to 4 seconds to overcome browser
    voice loading delays on Safari, Firefox, and mobile Chromium.
  - Implements Chrome keep-alive bugfix: Runs a 5-second interval that resumes speech if
    the browser's speech synthesis engine silently stalls.
- `startListening(langCode, handlers)`:
  - Uses `webkitSpeechRecognition` or `SpeechRecognition` configured with the farmer's language.
  - Returns interim transcripts in real time and triggers `onFinal` when the farmer stops speaking.
  - Gracefully ignores harmless `no-speech` timeout events.

5. CORE ARCHITECTURAL FEATURES & REAL-WORLD WORKFLOWS
================================================================================

--------------------------------------------------------------------------------
5.1 4-WAY MULTICHANNEL ACCESS ARCHITECTURE
--------------------------------------------------------------------------------
KisanFlow bridges the rural digital divide by offering 4 distinct access paths:

1. Web PWA: For smartphone farmers with high-speed internet.
2. DTMF Phone IVR (`1800-425-4747`): For farmers with basic ₹1,000 keypad feature phones.
   Works entirely via dual-tone telephone touch-tones and spoken audio.
3. Voice AI: For illiterate farmers who cannot read text. They simply speak into the phone
   in their native dialect and listen to spoken answers.
4. Village Assisted Desk: For walk-in farmers who do not own any phone. Field operators
   register them at the village level and issue printed slips.

--------------------------------------------------------------------------------
5.2 5-STAGE GROUND MANDI PROCUREMENT PIPELINE
--------------------------------------------------------------------------------
Standardizes and digitizes physical mandi operations:

[Stage 1: Gate Entry]
Tractor arrives at mandi gates. Security verifies token number and vehicle registration.
Status: `WAITING_FOR_GATE_ENTRY` ➔ `GATE_ENTRY_VERIFIED`.

[Stage 2: Quality & Moisture Assaying]
Government assayers test grain samples using electronic moisture meters.
Standard FAQ limit for Paddy is 14% (KisanFlow checks moisture % and certifies FAQ Grade A).
Status: `QUALITY_CHECK_PENDING` ➔ `QUALITY_CHECK_COMPLETED`.

[Stage 3: Weighbridge & Net Weight]
Tractor drives onto electronic weighbridge.
Gross Weight recorded (e.g. 85 Quintals).
Grain unloaded at yard.
Empty tractor drives onto weighbridge. Tare Weight recorded (e.g. 25 Quintals).
Net Weight computed automatically: 85 - 25 = 60 Quintals.
Weighbridge slip generated.
Status: `WAITING_FOR_WEIGHING` ➔ `WEIGHING_COMPLETED`.

[Stage 4: Bagging & Gunny Allotment]
Produce packed into standard 50kg jute gunny bags (60 Quintals = 120 bags).
System monitors gunny bag inventory and flags labour availability shortages.
Status: `BAGGING_PENDING` ➔ `BAGGING_COMPLETED`.

[Stage 5: J-Form & Direct Benefit Transfer (DBT)]
Digital J-Form receipt generated with government slip number.
Payout calculated: 60 Quintals × ₹1,950 (MSP) = ₹1,17,000.
Direct Benefit Transfer triggered to farmer's Aadhaar-linked bank account.
Status: `J_FORM_GENERATED` ➔ `PROCUREMENT_COMPLETED`.

--------------------------------------------------------------------------------
5.3 DYNAMIC QUEUE LOAD BALANCING & CONGESTION PREVENTION
--------------------------------------------------------------------------------
To prevent mandi traffic jams:
- System calculates real-time wait duration across all centres in the district.
- If Lakshmipur Centre has a 140-minute wait (overloaded), the system automatically
  prompts farmers: *"Ramapuram Centre is 9 km away with only a 15-minute wait.
  Switching will save you 1 hour 45 minutes."*
- District officers can adjust congestion threshold sliders to trigger proactive SMS alerts.

--------------------------------------------------------------------------------
5.4 AUDIO & SPEECH ENGINEERING UNDER THE HOOD
--------------------------------------------------------------------------------
1. DTMF Synthesis:
   Uses standard frequency pairs:
   - Low Group: 697Hz (Row 1), 770Hz (Row 2), 852Hz (Row 3), 941Hz (Row 4)
   - High Group: 1209Hz (Col 1), 1336Hz (Col 2), 1477Hz (Col 3)

```bash
npm install
```

```env
# Optional: Gemini API Key for Tier-1 LLM generation
VITE_GEMINI_API_KEY=your_gemini_key_here

VITE_SUPABASE_URL=https://pqconvvuhpvoqutgtmac.supabase.co

```

Step 3: Run Development Server
```bash
npm run dev
```
Open your browser and navigate to:
`http://localhost:3000`

Step 4: Build for Production
To verify type safety and produce optimized production artifacts:
```bash
npm run build
```
The production bundle will be generated in `dist/`. You can preview it with:
```bash
npm run preview
```
